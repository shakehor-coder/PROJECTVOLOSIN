# Задание 3 — многопоточность и асинхронность

## Что добавлено

В текущий ShopEase добавлен отчёт администратора `/Admin/Inventory`:
число активных товаров, количество отсутствующих товаров, число единиц на
складе и стоимость запасов по категориям. Ссылка «Остатки товаров» находится
в меню Admin. Предыдущая страница процессов сохранена.

## Где используется асинхронность

`InventoryController.Index` возвращает `Task<IActionResult>`. Запрос EF Core
заканчивается `await ToListAsync(cancellationToken)`: пока SQL Server выполняет
запрос, поток приложения не занят синхронным ожиданием ответа. Это помогает
обслуживать другие запросы при ожидании ввода-вывода, но не ускоряет сам SQL.
`AsNoTracking` отключает ненужное отслеживание прочитанных сущностей; проекция
выбирает только поля для расчёта, а не полные графы объектов.

После загрузки контроллер ожидает `InventoryAnalytics.AnalyzeAsync`.
Вычислительная работа запланирована через `Task.Run` на пуле потоков.
Это перенос CPU-расчёта, а не асинхронный запрос к базе. `Task.Run` сам по себе
не увеличивает пропускную способность веб-сервера: рабочие потоки и процессор
всё равно расходуются. Не используются `.Result` и `.Wait()`.

## Где используется многопоточность

После материализации данных `InventoryAnalytics` группирует неизменяемые
записи `InventoryItem` по идентификатору категории. Если загружено не меньше
1000 товаров и есть несколько категорий, `Parallel.For` рассчитывает
категории независимо. Параллелизм ограничен меньшим из числа процессоров
и 4. Фактическое распределение работы определяет планировщик .NET.
Для небольшого каталога используется обычный цикл.

Порог 1000 — учебная эвристика, не результат измерения производительности.
На небольших данных параллельный цикл может быть медленнее последовательного.
Измеренное ускорение в работе не заявляется.

## Какие проблемы решены

- Синхронное ожидание базы заменено асинхронным; освобождается поток на время I/O.
- Независимые расчёты по категориям могут использовать несколько ядер на большом каталоге.
- Лишние потоки не создаются вручную для каждой позиции; используется управляемый пул.
- Гонки при суммировании исключены: у каждой категории локальные счётчики и свой элемент массива результатов.
- Непотокобезопасный `DbContext` не передаётся рабочим потокам. Все обращения к нему завершены до `Parallel.For`.
- Отмена HTTP-запроса передаётся в запрос EF, `Task.Run`, `ParallelOptions` и проверки внутри расчёта.
- Категории с одинаковым именем не смешиваются: группировка по ID. Порядок результата фиксирован по ID.

## Проверка

```sh
dotnet build ShopEase/Ecommerce.csproj -c Release
dotnet run --project checks/InventoryChecks/InventoryChecks.csproj -c Release
```

Проверяются пустой каталог, точные денежные суммы, нулевые остатки,
последовательный путь на малых данных, параллельный путь на 10 000 товарах,
совпадение с независимым LINQ-расчётом, восемь одновременных запросов,
заранее отменённая операция и категории с одинаковым названием.

Сборка: 0 ошибок и 0 предупреждений. Проверки расчёта пройдены.
Полный запуск веб-страницы с SQL Server не проверен: в рабочем окружении нет
сервера базы. После настройки базы по README откройте страницу под Admin и
сравните показатели с товарами каталога. Изменение схемы и новые миграции не нужны.

## Ограничения

Каталог загружается целиком в память; для миллионов товаров лучше использовать
агрегацию SQL или порционную обработку. Ограничение в 4 работника действует
на один отчёт. В [задании 4](04_SYNCHRONIZATION.md) добавлен общий семафор,
разрешающий только один вычисляемый отчёт на процесс сайта. В рамках учебного
задания демонстрируется безопасный параллельный расчёт на данных в памяти.
Отчёт показывает состояние прочитанных данных; изменения склада после чтения
попадут в следующий отчёт.
