# Задание 4 — синхронизация

## Требование и решение

В проект внедрён `SemaphoreSlim(1, 1)`. Он разрешает только один одновременный
расчёт отчёта об остатках на экземпляр приложения. Остальные запросы ожидают
разрешения через `WaitAsync`, не удерживая поток синхронным ожиданием.
Механизм добавлен к отчёту задания 3; магазин и страница процессов сохранены.

## Что синхронизируется

В задании 3 каждый большой отчёт мог использовать до четырёх работников,
но несколько администраторов могли одновременно запустить несколько таких
отчётов. Теперь общий singleton `InventoryCalculationGate` ограничивает
вход в вычислительную часть `InventoryAnalytics.AnalyzeAsync`.

Асинхронное чтение SQL выполняется до входа в секцию. Семафор не блокирует
другие функции магазина и не является блокировкой записей в базе данных.
Внутри одного допущенного отчёта сохраняется параллельная обработка категорий.
Таким образом, синхронизация между запросами не отменяет многопоточность
внутри расчёта.

## Алгоритм

1. Контроллер загружает данные асинхронно и вызывает `AnalyzeAsync`.
2. `InventoryCalculationGate.ExecuteAsync` ожидает разрешение `WaitAsync`.
3. Получив разрешение, запускает переданный расчёт и ожидает его завершения.
4. В блоке `finally` вызывается `Release`, в том числе при исключении или отмене расчёта.
5. Следующий ожидающий запрос может войти в вычислительную секцию.

Ожидание `WaitAsync` находится перед `try`: если ожидающий запрос отменён,
он не получил разрешение и не должен вызывать `Release`. Это предотвращает
ошибочное увеличение числа доступных разрешений. Порядок FIFO не обещается.

## Почему выбран SemaphoreSlim

`lock` подходит для коротких синхронных секций (он уже используется монитором
процессов задания 2), но его нельзя удерживать через `await`. Здесь нужно
ожидать асинхронную операцию целиком, поэтому используется асинхронное
ожидание семафора. `SemaphoreSlim` координирует задачи внутри процесса,
а не разные серверы или приложения.

## Проверки

Из корня репозитория:

```sh
dotnet build ShopEase/Ecommerce.csproj -c Release
dotnet run --project checks/SynchronizationChecks/SynchronizationChecks.csproj -c Release
dotnet run --project checks/InventoryChecks/InventoryChecks.csproj -c Release
```

Проверка синхронизации удерживает первый расчёт открытым, ставит в ожидание
30 других запросов и отменяет дополнительный ожидающий запрос. Затем
подтверждает отсутствие одновременного входа, завершение всех задач и
сохранение их результатов. Отдельно проверяются освобождение разрешения
после исключения и после отмены уже выполняющегося расчёта.
Проверки используют общий экземпляр реального сервиса, не требуют SQL Server.

## Ограничения

Механизм действует на один процесс сайта. Несколько экземпляров сайта
будут иметь разные семафоры. Размер очереди ожидания и загрузка SQL-запросов
не ограничены; данные ожидающих отчётов уже находятся в памяти. Для высокой
нагрузки нужны ограничение очереди, кэширование отчётов или отдельный сервис
фоновых задач. Механизм не исправляет конкурентное изменение остатков при
оформлении заказов — это другая критическая секция с требованиями к транзакциям.
