# Запуск, размещение и проверка магазина

## Два режима базы

SQL Server сохранён. Теперь перед созданием ролей применяются его миграции,
что устраняет обращение к таблицам Identity до создания схемы.
Для локальной демонстрации и временного тестового хостинга добавлен SQLite:
`Database__Provider=Sqlite`. Если строка подключения не задана, используется
`App_Data/shop.db`. Для новой SQLite-базы схема создаётся EnsureCreated;
SQL Server-миграции на неё не накатываются. Последующее изменение схемы SQLite
требует отдельной миграционной стратегии, автоматического обновления здесь нет.

В SQLite денежные поля хранятся как целое число копеек/центов и преобразуются
в decimal; сортировка по цене выполняется в базе без потери точности на двух
десятичных знаках. Это отдельный демонстрационный файл, существующая база
SQL Server не переносится автоматически.

Ключи Data Protection находятся в App_Data/keys. Настройки реестра, корзины
и состояния процессов по-прежнему хранятся в памяти и сбрасываются при рестарте.

## Локально без SQL Server

PowerShell из корня репозитория:

```powershell
$env:Database__Provider = 'Sqlite'
$env:SeedAdmin__Email = 'admin@example.test'
$secret = Read-Host 'Пароль администратора' -AsSecureString
$env:SeedAdmin__Password = [System.Net.NetworkCredential]::new('', $secret).Password
dotnet run --project ShopEase/Ecommerce.csproj --launch-profile http
```

Пароль должен удовлетворять правилам ASP.NET Identity. На повторном запуске
существующий пароль пользователя автоматически не меняется. Сайт доступен
по адресу http://localhost:5134. Без SeedAdmin__Email можно зарегистрировать
обычного покупателя, но административный аккаунт не создаётся.

## Docker

```sh
docker build -t shopease .
docker run --rm -p 8080:8080 -v shopease-data:/app/App_Data \
  -e SeedAdmin__Email -e SeedAdmin__Password shopease
```

Переменные администратора предварительно задаются в окружении, секреты
не вписываются в Dockerfile. Volume сохраняет SQLite и ключи между запусками.
Healthcheck endpoint: `/health`. Контейнер настроен на порт 8080.
Dockerfile проверен по структуре и через dotnet publish; сам Docker-образ
в текущей среде не собирался, поскольку Docker отсутствует.

## Render

В корне есть render.yaml с тестовым web service на плане free.
Подключить репозиторий через Blueprint. Пароль администратора генерируется
Render в переменной SeedAdmin__Password, email — admin@example.test.
Проверить выбранный план и лимиты в панели перед созданием сервиса.
Публичное размещение требует подключённого аккаунта Render.

Важно: у тестового варианта нет постоянного диска. SQLite, ключи и аккаунты
могут пропасть после рестарта/пересоздания сервиса. Это демонстрация, а не
размещение рабочего магазина. Для сохранения данных нужен постоянный диск
или отдельная база и продуманная миграция. Не использовать реальные заказы.

Официальные справочники:
https://render.com/docs/blueprint-spec
https://render.com/docs/free
https://render.com/docs/docker

## Выполненные проверки

- Release-сборка веб-приложения и отдельной DLL — успешно, 0 ошибок и предупреждений.
- InventoryChecks — точные суммы и параллельный расчёт.
- SynchronizationChecks — взаимное исключение, исключения и отмена.
- HookRegistryChecks — атомарные обновления, событие успеха, отсутствие события при ошибке/отмене, отписка и загрузка отдельной DLL.
- ProcessChecks — запуск, завершение, потоки вывода и остановка.
- Реальный HTTP-тест запущенного приложения с отдельной временной SQLite-базой — успешно.

HTTP-тест проходит вход администратора, запрет административного доступа
покупателю, регистрацию покупателя, отчёт, обновление реестра, событие хука,
запуск процесса, сортировку каталога по цене, корзину, оформление заказа,
историю заказов и очистку корзины. Неверный адрес доставки возвращает 400.
Дополнительно в оформлении заказа проверяется принадлежность выбранного адреса
текущему пользователю; пустые поля нового адреса отклоняются.

Повторение HTTP-проверки после Release-сборки (Node.js 22+ и .NET 8):

```sh
node checks/http-smoke.cjs
```

При нестандартном пути к dotnet задать SHOP_SMOKE_DOTNET. Скрипт создаёт
одноразовую базу в системном временном каталоге, запускает и останавливает
сервер сам; не направлен на размещённую пользовательскую базу.

## Ограничения подтверждения

Общий браузер не достигает локального сервера этой среды. Запуск отдельного
Chromium завершился ошибкой socket(): Operation not permitted. Поэтому
визуальная проверка страниц в браузере не подтверждена; пройдены HTTP-сценарии.
Публичный URL не получен: Render ещё не подключён. SQL Server-режим после этих
изменений с настоящим SQL Server отдельно не запускался.
