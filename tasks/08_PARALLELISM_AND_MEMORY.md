# Задание 8 — параллельное выполнение и управление памятью

Два полученных файла содержат одинаковый текст задания, поэтому это описание
относится к обоим. Примеры ниже взяты из текущего проекта.

## Параллельное выполнение

| Механизм | Применение и принцип |
| --- | --- |
| Task и async/await | Контроллер отчёта ожидает ToListAsync. Ожидание I/O не удерживает поток; async сам по себе не создаёт новый поток |
| Task.Run | CPU-расчёт выполняется в пуле потоков; это перенос работы, а не увеличение производительности сервера автоматически |
| Parallel.For | Независимые категории рассчитываются параллельно, максимум min(4, число процессоров); для малого каталога обычный цикл |
| SemaphoreSlim | Общий экземпляр разрешает один отчёт одновременно; WaitAsync не блокирует ожидающий поток |
| lock | Защищает общий реестр и состояние дочернего процесса при конкурентных запросах |
| CancellationToken | Позволяет отменить SQL-запрос, ожидание семафора и расчёт; отмена кооперативная |
| Process | Диагностика запускается в отдельном процессе с собственным PID и адресным пространством |

Пример асинхронного I/O: `await query.ToListAsync(cancellationToken)`.
Пример CPU-параллелизма: `Parallel.For(0, groups.Length, options, CalculateCategory)`.
Пример синхронизации: `await semaphore.WaitAsync(token); try { ... } finally { semaphore.Release(); }`.

Нельзя одновременно выполнять EF-запросы через один DbContext. В проекте
сначала получаются данные, затем неизменяемые DTO передаются вычислению.
Работники используют локальные суммы и разные элементы массива результата,
поэтому общей изменяемой суммы между потоками нет.

## Управление памятью в C# и .NET

Объекты, массивы и строки обычно выделяются в управляемой куче. GC отслеживает
достижимость и освобождает недостижимые объекты; разработчик не вызывает free.
Поколения 0, 1 и 2 позволяют чаще собирать короткоживущие объекты. Большие
объекты могут попадать в LOH, поэтому загрузка всего каталога имеет цену.
Гарантированного момента запуска GC нет; GC.Collect в проекте не используется.

В отчёте создаются снимок массива, группы и массив результатов. Они имеют
время жизни операции и могут быть собраны после потери всех ссылок.
Singleton-реестр и издатель событий остаются достижимыми до остановки хоста.
Сервис хранит только последний снимок реестра, а ProcessMonitor ограничивает
консольный вывод 16 000 символами, чтобы он не рос бесконечно.

GC не заменяет освобождение внешних ресурсов. Process.Dispose освобождает
ресурсы объекта Process, а Kill завершает сам дочерний процесс — это разные
операции. Транзакции базы оформлены `using`; DbContext создаётся на HTTP-scope
и освобождается контейнером DI. Событийный хук отписывается при StopAsync,
чтобы долгоживущий издатель не удерживал обработчик.

`record` не означает автоматическую потокобезопасность, но здесь DTO имеют
init-свойства, а снимок реестра заменяется целиком под lock. Сервис не выдаёт
изменяемую внутреннюю коллекцию. decimal используется для денежных расчётов.

## Другие доступные механизмы

Для больших потоков задач можно применять Channel с ограниченной ёмкостью,
для повторного использования буферов — ArrayPool с возвратом в finally,
для последовательной обработки потока данных — IAsyncEnumerable.
Их в текущем решении нет: добавлять их без задачи и измерений не требуется.

## Ограничения

Все семафоры, реестр и счётчики относятся к одному процессу сайта. Снимки
каталога ожидающих запросов занимают память. Для большой нагрузки нужны
ограничение очереди и/или SQL-агрегация. Ускорение на маленьком каталоге
не обещается; сравнение производительности требует отдельных измерений.
